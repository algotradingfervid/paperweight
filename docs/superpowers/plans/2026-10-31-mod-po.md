## Global constraints

- **Packages.** Use the package for the layer you're working in:
  - `internal/modules/modkit`: shared module helpers, settings and comments.
  - `internal/modules/purchase`: services and DocTypes. Never imports `internal/ui`.
  - `internal/modules/purchase/web` (package `purchaseweb`): screens, hooks and module routes.
  - `internal/app`: wiring only.
  - Import direction: a module imports kernel, masters and `modkit`; `purchase/web` may also import `internal/ui` (CD-237, Task M0-6 guard).
- **Migrations.** `migrations/10000–10049` for `modkit` and `migrations/10050–10199` for `purchase` (spec §14.5). Each package's `sqlc.yaml` lists its own migration files plus the master migrations it joins (CD-117). Unreleased migrations are edited in place.
- **Tables.** Every id is `INTEGER PRIMARY KEY AUTOINCREMENT` (CD-156). Line tables have `id`, `parent_id` ON DELETE CASCADE and `line_no` (CD-161).
- **Writes.** Every write goes through `db.Write`. Cross-record checks read inside the write. Every web write posts `version` (CD-94, CD-183). Inside a transaction use the Tx twins (`CanTx`, `UsersWithRightTx`, …), never a second connection (CD-213, CD-224).
- **Messages.** Every message is copied exactly from the spec into a catalogue file owned by its task (`messages_<area>.go`). One condition per message (CD-147). Refusals from other packages are expected by their exact text (CD-142).
- **Scope.** Restriction- and scope-dependent behaviour gets at least one test on the real `auth.Service` (§10 lessons). Lists, counts and hints read through `Auth.Scope` (AUTH-110).
- **Tests.** The test-first rule from the protocol applies. High-tier tasks get their tests from a test-writer, committed before code. Every behaviour named in a task has a test that fails when its call site is deleted (`make covertouched`).
- **UI.** Every screen is built from `components.*` and `FieldInput` through the docscreen hooks. No daisyUI classes outside `internal/ui`, no inline style or script, and no new component unless the approved UX design names it. Run `make generate` before every UI hand-in.
- **Temp files.** Temp file names carry the task label (shared scratchpad).

## File ownership: how parallel tasks avoid collisions

The serial tasks **M0-6** (modkit skeleton) and **P1** (purchase skeleton) create every shared file once, with stubs that return nil, zero or `501 Not implemented yet`:

- `purchase/hooks.go`: the `doctype.Hooks` methods, each delegating to one function in a per-task file.
- `purchase/register.go`: DocTypes, rights and `RegisterQtyUse`.
- `purchaseweb/routes.go`: every module route, each pointing to a handler in a per-task file.
- `purchaseweb/module.go`: the `docscreen.Module` values, each field pointing to a per-task function.

After that, every task owns only its own files. A lane task never edits `hooks.go`, `register.go`, `routes.go` or `module.go`. If it must, it stops with `CONTRACT-CR`. Generated files (`dbq/`, `*_templ.go`, static assets) conflict on rebase; resolve those by regenerating (CLAUDE.md).
