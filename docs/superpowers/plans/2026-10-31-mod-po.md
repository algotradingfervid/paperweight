## Global constraints

**Packages.**
- `internal/modules/modkit`: shared module helpers, settings and comments.
- `internal/modules/purchase`: services and DocTypes. It never imports `internal/ui`.
- `internal/modules/purchase/web` (package `purchaseweb`): screens, hooks and module routes.
- `internal/app`: wiring only.
- A module imports kernel, masters and `modkit`. `purchase/web` may also import `internal/ui` (CD-237; M0-6 adds the guard).

**Data.**
- Migrations: `migrations/10000–10049` for `modkit`, `10050–10199` for `purchase`. Each package's `sqlc.yaml` lists its own migrations plus the master migrations it joins (CD-117). Unreleased migrations are edited in place.
- Every id is `INTEGER PRIMARY KEY AUTOINCREMENT` (CD-156). Line tables have `id`, `parent_id` ON DELETE CASCADE and `line_no` (CD-161).
- A field that a module route sets on create (`request_line_id`, `copied_from_no`) is never `ReadOnly`, because `checkReadOnly` refuses it. It is hidden with `Module.Hide`, and its rules live in `Validate`.

**Writes.**
- Every write goes through `db.Write`.
- Cross-record checks read inside the write.
- Every web write posts `version` (CD-94, CD-183).
- Inside a transaction use the Tx twins (`CanTx`, `UsersWithRightTx`, …), never a second connection (CD-213, CD-224).

**Messages.**
- Each message is copied exactly from the spec into a catalogue file owned by its task (`messages_<area>.go`).
- One condition per message (CD-147).
- Other packages' refusals are expected by their exact text (CD-142).

**Tests.**
- Restriction- and scope-dependent behaviour gets at least one test on the real `auth.Service`.
- Lists, counts, queues and hints read through `Auth.Scope` (AUTH-110).
- Test-first, per the protocol. High tier gets tests from a test-writer, committed first.
- Each named behaviour has a test that fails when its call site is deleted (`make covertouched`).
- Research test patterns (CD-272, report §2), for every task:
  - **Do and undo in one test.** Each effect test asserts the state after the action and after its reversal (cancel, close, amend, clear, delete).
  - **One builder per DocType through the real path.** `purchasetest` (P1) has `NewOrder(t, env, opts…)` and `NewRequest(t, env, opts…)` that drive `Engine.Do` (save, submit, approve as the right users) with stop-at options (`StopAtDraft`, `StopAtPending`, `StopAtApproved`). No test inserts document rows with SQL, except schema and trigger tests.
  - **Exact messages.** Every refusal and warning is asserted by its full text, including DOC's `Line {n}: ` prefix (CD-264 (8)).
  - **Quantity walk tables.** Roll-up cases (PO-030, PO-055, PO-076 to PO-078) are table-driven: one row per step with the expected ordered, held, received and pending figures.
  - **Rollback by row counts.** Each refusal on a write path asserts that the row counts of the tables it touches are unchanged.
  - **Frozen clock.** Date rules run on a fixed clock (`authtest.T0` = 24-10-2026 10:30 IST, or the date the case names), never `time.Now`.
  - **The CD in a comment.** Each test names the case id and the CD or spec section it guards in its doc comment.

**UI.**
- Everything is built from `components.*` and `FieldInput` through the docscreen hooks.
- No daisyUI classes outside `internal/ui`, and no inline style or script.
- No new component unless the approved UX design names it.
- Run `make generate` before every UI hand-in.

**Temp files** carry the task label.

### M0-13 · DOC reassign (H)

**Spec.** §21.2, §15 item 13.

**Files.**
- `internal/kernel/doc/reassign.go`
- `internal/kernel/doc/contract.go` (additive `Reassign`)
- `internal/kernel/doc/messages.go` (only the `ReassignError` kinds)
- `docfake` (refuses it: CD-186)
- tests

**Do.** `Reassign(ctx, p, doctype string, id int64, version int, to types.UserID) error`. Inside `db.Write`, in this order:
1. Load the document and check its version.
2. Check the state. Pending gives reason `Pending`. Approved, closed and cancelled give `NotDraft`.
3. The caller is the owner, or holds `approve` (`CanTx` with the record). Otherwise AUTH's 403.
4. `to` equal to the owner gives `SameOwner`.
5. Check the target:
   - disabled: `Disabled`;
   - `create` and `read` on the record (`CanTx` as the target): failing gives `CantCreate` or `CantSee`;
   - `write` on a copy of the `RecordRef` with `CreatedBy = to`.

## Phase 1: services (`internal/modules/purchase`, branch `wp/mod-po`)

From P2 on, each task runs in its own lane worktree, `.worktrees/mod-po-<task>`, and rebases onto `wp/mod-po` after each merge into it. Every task deletes its own `stubs_<task>.go` and `stubs_web_<task>.go` and adds its own files; no task edits another task's file (CD-256).

**Service shape (P1; every later task follows it).**
- Hooks and the frozen tx calls (`RefreshReceiptStatus`, `SetRestNotComing`) are package functions that read and write only through the `tx` they are given. What they need beyond the tx comes from one package-level `modkit.Wiring[Hooks]` (AD-9's M0-27, CD-284), keyed by database: `purchase.Wire(d *db.DB, Hooks{Clock clock.Clock; Comments *modkit.Comments})` calls its `Wire(d, v)`, and every hook and frozen call reads it with `Get(tx)`. `app.New` wires its own DB, and each `purchasetest.Env` wires its own, so parallel worlds never share an Auth or clock. A `Get` for an unwired database is a plain internal error.
- Everything that acts for a principal is a method on `*purchase.Service`, built per environment by `purchase.New(ServiceDeps{DB *db.DB; Engine doc.Engine; Auth auth.Service; Audit audit.Writer; Approvals *approval.Approvals; Comments *modkit.Comments; Clock clock.Clock})` in P1's `service.go`. Each task adds its methods in its own file.
- `purchasetest.Env` builds the DB, the real `auth.Service`, the engine and one `*purchase.Service`, and passes the same `*clock.Fixed` to the engine, auth, approvals, comments and `Service`. `env.SetNow(t, at)` moves the shared clock and restores it in `t.Cleanup`; tests that move it never call `t.Parallel`.
- Writes inside the frozen tx calls and `RefreshOrderStatus` are plain UPDATEs: no `version` bump, no `updated_at`/`updated_by` and no audit entry. They have no principal, and the rows they touch (submitted requests, approved or closed POs) can't be edited, so no CD-94 save races them. This differs from `doc/rollup.go:82`, which bumps the version (CD-280).
- Module warnings (Already received above qty, over-request, site and project state) have no kernel channel: `Hooks.Validate` returns only refusals (`doc/save.go:78`). `(*Service).OrderWarnings(ctx, p, poID) ([]string, error)` (P2) returns them, read in one read tx with the read check, and the check page shows them (P15a). P6 adds its texts through a stub in `stubs_p6.go` (`requestWarnings`), not by editing P2's file (CD-280).
