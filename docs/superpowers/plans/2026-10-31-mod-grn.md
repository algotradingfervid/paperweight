## Global constraints

**Packages.**
- `internal/modules/goodsreceipt`: services, the DocType, hooks, bill details, reports. It never imports `internal/ui`. It imports kernel, masters, `modkit` and `purchase` (`goodsreceipt → purchase`, M0-6's order `modkit` < `purchase` < `goodsreceipt` < `expense`).
- `internal/modules/goodsreceipt/grntest`: the module's test environment (real engine, real `auth.Service`, real `files.Store`, `purchase` registered).
- `internal/modules/goodsreceipt/web` (package `grnweb`): screens, docscreen hooks, module routes. May import `internal/ui` (CD-237; M0-6's guard).
- `internal/app`: wiring only.
- `purchase` never imports `goodsreceipt`; the PO page reads GRNs through `doc.LinkedBlockers` (PO spec §11).

**Data.**
- Migrations `migrations/10200–10349` (PO spec §14.5): `10200_goods_receipt.sql`, `10210_grn_bill.sql`. Unreleased migrations are edited in place.
- `goodsreceipt/sqlc.yaml` lists its own migrations plus every migration whose tables it reads (CD-117): the purchase migrations P1 creates (`10050_purchase_order.sql`, and any later purchase migration that alters `purchase_order` or `purchase_order_line`), the party, address, item, uom, site and project migrations, the audit migration, the attachments migration (G9's photo count) and the users migration. Check every file name against `migrations/` on `main` at dispatch.
- Query names in `queries/*.sql` carry their task's prefix (`G2PO`, `G3Accepted`, `G7Bill`, …); shared reads live in G1's `base.sql`, so lanes that each add `queries/<task>.sql` never clash in the one `dbq` package.
- Every id is `INTEGER PRIMARY KEY AUTOINCREMENT` (CD-156). `goods_receipt_line` has `id`, `parent_id` ON DELETE CASCADE and `line_no` (CD-161). `grn_bill` has its own `id`, `grn_id` UNIQUE REFERENCES `goods_receipt(id)`, `version`, and audit columns.
- Convention columns (`number`, `state`, `created_by`, …) are declared only as read-only fields mapped to themselves (CD-144). Field names are unique across header and lines (CD-151): header `received`-style names don't clash today; check at G1.
- **Posted, not System** (spec §3.1): `site_id` and `project_id` are plain `Int` header fields, posted by step 1 from the PO and reset from the PO by `Validate`, so `create`'s rights check sees them (`doc/save.go`). `po_line_id` is a plain `Int` line field, posted by step 3. None of the three is `ReadOnly` (`checkReadOnly` refuses a posted read-only value on create, CD-247 item 1); `Module.Hide` hides them and `Validate` owns their rules.
- **System and ReadOnly:** `vendor_id` (Link Party) and line `uom_id` (Link UoM): copied from the PO in `Validate`, never posted, never master-checked.
- **Other header fields (v0.5):** `challan_kind` (Select, Options `Delivery challan` and `Tax invoice`: the stored values are the display texts, so every generic surface reads right; CD-175) and `rest_not_coming` (Check), both `Step: "delivery"`. `challan_no` is labelled `Challan or invoice no.`.
- **ReadOnly computed:** `accepted_value` (header Money) and line `accepted_qty` (Qty), written by `Validate`.
- **Snapshot columns, not Fields:** header `snap_po_id`, `snap_vendor_name`, `snap_vendor_gstin`, `snap_vendor_address`, `snap_po_number`, `snap_po_date`, `snap_site_name`, `snap_project_code`, `snap_branch_id`; line `snap_item_code`, `snap_item_name`, `snap_hsn_sac`, `snap_uom_code`, `snap_rate`, `snap_is_service`. `snap_po_id` (the PO the snapshots came from) and `snap_is_service` (the item is a service) are this plan's additions: the first drives GRN-004, the second the challan rule and the print dash.

**Hooks (no principal).** `doctype.Hooks` methods get `(ctx, tx, id)` only.
- DocTypes register at `init`, so the hooks read their dependencies per database through AD-9's `modkit.Wiring[T]` (M0-27, CD-284): G1 defines one package-level `modkit.Wiring[Deps]` with `Deps{DB *db.DB; Clock clock.Clock; Auth auth.Service; Audit audit.Writer; Files *files.Store}` (check the audit writer's type name on `main` at dispatch; services that open their own `db.Read`/`db.Write`, G6, G7 and G9, use the same value). `app.New` wires it with `Wire(db, deps)` for its database, and `grntest` does the same for each test world, so many worlds per binary (some parallel, in internal/app and e2e) each get their own value. Hooks call `Get(tx)` and read only through the `tx` they are given; services take `Deps` from their constructor or `Get` on their own transaction. `Auth.Scope` has no Tx twin, so services call it before opening a transaction (nestcheck). `Get` on an unwired database returns its error, which the hook returns as a plain internal error (CD-284; check `modkit.Wiring`'s exact API on `main` at dispatch).
- `Validate` runs on every draft save and again inside submit and approve (`doc/transitions.go` `revalidate`), so it can't tell a save from a submit. Rules the spec marks **Submit** go in `BeforeSubmit` and return field errors through `doc.Invalid(fields)` (MOD-EXP X1, CD-264 (2)); whole-document refusals return `doc.Refused(msg)`.
- `hooks.go` composes every hook from per-task functions:

| Hook | Composition |
|---|---|
| `Validate` | `validateReceipt` (G2) |
| `BeforeSubmit` | `checkLock` (G5, as a `receipt_date` field error, CD-282 Q9) + `submitFields` (G2), returned together as one `doc.Invalid` only when there are errors (`doc.Invalid(nil)` is a non-nil error) |
| `ApplyEffects` | `applyReceipt` (G3) → `copyBillOnAmend` (G7) → `restNotComing(on)` (G10) |
| `ReverseEffects` | `checkLock` (G5) → `reverseReceipt` (G3) → `restNotComing(off)` (G10) |
| `Amount` | `accepted_value` (G1; no rule is seeded, so it matters only if an owner adds one) |
| `Date` | `receipt_date` (G1) |

**Writes.**
- Every write goes through `db.Write`; cross-record checks read inside it (CD-94).
- Every web write posts `version` (CD-183); module routes too. The bill record has its own version, 0 when there's no row (the PO sent record's rule, CD-247 item 6).
- Inside a transaction use the Tx twins (`CanTx`, `CheckLinkTx`, `HasRoleTx`), never a second connection (CD-213, CD-224). The nestcheck gate runs in `make test`.
- The PO's `received_qty` is the kernel roll-up's. GRN never writes it. `receipt_status` is written only by `purchase.RefreshReceiptStatus`, with the accepted totals GRN computes inside the transaction.

**Messages.**
- Each text is copied exactly from GRN spec §3.3, §4 and §5 into a catalogue file owned by its task (`messages_<task>.go`). One condition per message (CD-147). Line texts start `Line {n}: ` (CD-264 (8)).
- Texts naming another record name it only when the viewer can read it, checked in the same read (CD-233, CD-240, CD-248). The GRN's own snapshot of its PO (`snap_po_number`) is a stored link on a record the viewer already reads, so it may be shown (CD-217, CD-228). The duplicate-invoice warning names another GRN, so it needs the read check (G7).
- Other packages' refusals are expected by their exact text (CD-142): DOC-017 (closed source), DOC-038 (cancelled source), DOC-052 (blocked cancel), R8 (no lines), DOC-069 (stale), AUTH-101 as amended by CD-240 (`You can't use this Purchase Order. It isn't available to you.`), AUTH's 403, `uom.CheckLineQty`'s whole-number text, M0-7's lock text, G0a's close text.

**Tests.**
- Test-first. High tier: a test-writer writes the task's tests from this plan and `grn.md`; they're committed first; the implementer may not change them.
- Restriction-, scope- and visibility-dependent behaviour has at least one test on the real `auth.Service` (GRN-001, 002, 015, 022, 029 always). Concurrency tests run as non-admin users (CD-213).
- Each named behaviour has a test that fails when its call site is deleted (`make covertouched BASE=<task base> PKGS=...`).
- Test literals that enter a validated API (series, quantities, dates) are checked against the validator first. `GR/26-27/00001` is 14 characters.
- **Research §2 patterns (CD-272), in every task:** `grntest` builders go through the real engine with stop-at flags (draft, submitted, approved); every effect test asserts after the action and after its reversal (do and undo); refusals assert the exact text and that nothing was written, rollbacks by row counts; quantity cases are walk tables before any fuzz; the clock is frozen (`authtest.T0`, 2026-10-24 10:30 IST); each test's comment cites the CD it guards. Scenario cases (GRN-037 on) also cite their research source in a comment.
- POs in tests are real `purchase.Order` documents made through the engine with `grntest` helpers; no test-local stand-in for the PO or the GRN (CD-125, PO spec §18).

**UI.**
- Built from `components.*` and `FieldInput` through the docscreen hooks only. No daisyUI classes outside `internal/ui`, no `style=`, inline scripts, `hx-on` or trigger filters.
- No new component unless the approved UX design names it.
- Directors run `make generate` and the `internal/ui` tests from their own session (the Tailwind binary hangs in the agent sandbox; lessons §11). Workers regenerate only `dbq/` (`sqlc`) and single templ files (`go tool templ generate -f <file>`).

**Temp files** carry the task label (`mod-grn-g3-...`).
