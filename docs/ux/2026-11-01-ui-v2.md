## 1. Goal

After UI v2 ships, a site engineer on a 390 px phone can sign in, raise a purchase order with a new vendor, and submit it in under three minutes. They don't need to know which fields matter: each step says what it is for, every link field searches as they type, dates pick from a calendar, and amounts group as they type. The same screens look calm and orderly on an office desktop. Measures:
- A first-time user raises a PO with 3 lines on a phone in under 3 minutes, with no help (owner walk-through, three people).
- Zero horizontal overflow and zero axe-core WCAG 2.2 AA violations on every route at 320, 360, 390, 768, 1024 and 1440 px (existing gates).
- Every phone wizard step passes "no field hidden under the sticky footer" (new e2e check, §8 A-12).
- The owner signs off on the mocks before any build task starts.

## 3. Jobs and flow

### 3.1 Jobs

- When I open the app on site, I want to see what is waiting for me and start a new document in one tap, so I can get back to work.
- When I fill a long form on a phone, I want it in short steps that explain why each field matters, so I don't guess or abandon it.
- When I need a vendor, item, site or project, I want to type a few letters and pick from a list showing code, GSTIN and city, so I pick the right one. If it doesn't exist, I want to add it without losing my order.
- When I type a date or an amount, I want a calendar and live commas (₹1,50,000.00), so I can read back what I typed.
- When something goes wrong, I want to be told what and how to fix it, next to the field, and to keep everything I typed.
- When I submit, I want a clear confirmation and to see where the document stands (Draft → Pending approval → Approved → Sent → Received).

### 3.2 Main flow: a new PO with a new vendor, on a phone

1. Bottom nav **New** → the "Create new" sheet → **Purchase order** (or Purchase home → quick action).
2. Wizard focus mode opens: the wizard head (`×`, "New purchase order", "Not saved yet") with a 4-step stepper. Step 1 **Details** says "Who you're buying from, where it goes and when you need it."
3. Vendor: tap the picker → a full-screen search sheet opens with **Recent** first. Type "sai krupa" → no match → **New vendor "sai krupa"** → the quick-create sheet (Name, GSTIN with live state check, City) → **Add and choose** → back on step 1 with the vendor chosen.
4. Deliver to is already chosen (only one site allowed). Order date shows today; **Today** / **Yesterday** chips; the calendar button opens the platform picker (CD-336).
5. **Save and continue** creates Draft 57; the save cue now reads "Saved 10:42". Steps 2 (Terms) and 3 (Items) follow; line cards with a sticky running total.
6. Step 4 **Check** shows a summary card per step with Change links, the totals and GST split, the approval preview, and **Submit for approval**.
7. The document page opens with the animated success tick "Submitted for approval", the status timeline at "Pending approval", and Withdraw in the action bar.

### 3.3 Alternative and failure paths

| Case | What the user sees |
|---|---|
| No rights for a page or record | Friendly problem page (§5.14): icon, "We can't open this page", the kernel 404 text exactly ("This record doesn't exist or you don't have access to it.") or the 403 text, then **Go to Home** and **Search** |
| Nothing to show | `EmptyState` with an object icon, a heading, one helpful line, and at most one action (never a second primary) |
| Validation error (422) | `ErrorSummary` at the top of the step ("2 things to fix before you continue"), focused, each item a link to its field; each field outlined in 2 px danger with an icon and plain text; typed values kept |
| Stale version (409) | Warning banner with the DOC text exactly ("Someone else changed Draft 57 after you opened it. Reload it and make your changes again."), the typed values still on the page, and a **Reload Draft 57** button |
| Record changed state underneath | APR's stale message as a warning banner, with a link to the record |
| Server busy (503) or 5xx | Danger banner in `#alerts`: "The server is busy. Try again in a minute." with **Try again** |
| Network dropped (htmx `sendError`) | Danger banner: "Couldn't reach the server. Check your connection. Nothing you typed is lost." with **Try again** |
| Slow answer (> 300 ms) | 3 px top loading bar; the pressed button shows a spinner and its busy label ("Saving…") |
| Upload in progress | Progress bar with percent and "Uploading bill-2.jpg…"; Save is disabled until it ends (CD-310) |

## 5. Screens and patterns

Each pattern names the component it maps to in `internal/ui/components` (or `layout`, `wizard`), marked **existing**, **changed** or **new**. §6 lists the new and changed ones with reasons. §10 is the build plan.

### 5.1 Visual language

**Direction.** Calm, bright, and orderly: white cards on a cool light-grey canvas, one blue accent for action and selection, generous spacing, larger corner radii, a small icon tile beside each section heading, and tabular figures for money. Modern comes from hierarchy, rhythm and motion, not from new colours. The existing token values stay wherever their contrast is already proven (`contrast_test.go`), so the build changes few colours and many layouts.

**Colour tokens** (`internal/ui/css/tokens.css`; brandable keys per CD-296's theme file):

| Role | Token | Value | Use | Change |
|---|---|---|---|---|
| Canvas | `--color-canvas` | `#F5F6F8` | Page background, **also on `html`** (R4, DL A7) | fix |
| Surface | `--color-surface` | `#FFFFFF` | Cards, inputs, header, sidebar, sheets, footer | same |
| Sunken | `--color-sunken` | `#EDEFF2` | Segmented track, skeleton, read-only, number badges | same |
| Text / secondary / muted / disabled | `--color-text…` | `#141A23` / `#46505E` / `#5E6878` / `#8A93A1` | As today; placeholders use **muted** (5.6:1) | same |
| Border / subtle | `--color-border` / `--color-border-subtle` | `#7C8696` / `#DCE0E6` | Input and button edges (3.7:1) / card outlines and dividers | same |
| Accent 50 / 100 / 600 / 700 / 800 | `--color-primary-*` | `#EEF3FF` / `#DDE8FE` / `#1F4FD1` / `#1A3FA8` / `#16348A` | 600: primary fill, links, focus, current step and nav bar. 50: selected rows, icon tiles. 100 (new, from DL §3.1): pressed state, focus halo on inputs. 800: text on tints | 100 added |
| Status ×4 | `--color-{success,warning,danger,info}-{50,600,700,800}` | as today | badges, banners, field errors, timeline | same |
| Overlay | `--color-overlay` | `rgb(20 26 35 / 0.5)` | sheet and dialog backdrop | same |

One brand accent only. Status colours and neutrals are never themed (DS §5.1, DL P3). A themed accent never carries meaning: Closed stays neutral (DL §3.1).

**Dark mode: not provided.** DS §1.2 makes light mode a product rule ("never", DS §11), DL §3.10 confirmed it, and per-deployment theme files (CD-296) would need a second full palette per company. It is not cheap, so no dark tokens are proposed. Q1 asks the owner only if he wants to reopen the rule.

**Type** (Inter, as today): display 24 px phone / 30 px from 48rem, weight 650; title 20/600; heading 18/600; body and every input 16/400 (no iOS zoom); label 16/550; meta 14; caption 13 (badges, step labels, counts only); uppercase 12 px tracking 0.06em only for sidebar group headings and picker section headings. Money and quantities use `font-variant-numeric: tabular-nums`. At most three sizes on a phone screen besides the h1 (DL §3.2).

**Spacing**: the 4 px grid. Field gap 20 px, card padding 16 px (phone) and 24 px (≥48rem), card gap 16 px, section gap 24 px. Gutter 16 / 24 px.

**Size**: controls are **48 px** tall on every width (was 44: the extra 4 px makes text inputs easier to hit with gloves and gives inputs room for prefix and suffix). Buttons stay 44 px minimum and 48 px in the footer. Bottom nav 64 px plus the safe area. Header 56 px.

**Radius** (v2, replaces DS §5 radius row; DL's `default` preset becomes): badge and chip pill; small 8 (icon tiles, segment thumbs); **input and button 10**; **card 14**; **sheet and dialog 20**. The `compact` and `round` presets of DL §3.3 scale from these.

**Elevation**: cards are flat with a 1 px subtle border and `--shadow-card` (a 1–2 px shadow). Shadows grow only on things that float: the sticky footer (`--shadow-raised`, an upper edge), picker dropdown and sheets (`--shadow-pop`). No other shadows.

**Iconography** (owner, 01-11; amends DL §4.2):
- One set: **Lucide, already vendored at `lucide-static` 1.61.0** under `internal/ui/icons/lucide/`. Never a CDN. New glyphs are copied from the same pinned release into that folder and listed in `icons.txt`. That adds no dependency, since the package and its licence are already in the repo. DL §4.1's re-pin to 1.65.0 stays optional.
- **Stroke 1.5 px** (owner) in place of DL's 2 px. The generator writes `stroke-width="1.5"` on every icon; at 16 px that renders about 1 px, which still meets 3:1 for non-text contrast in our colours. Exceptions at 2–2.5 px: the check inside a done step dot, the plus in the bottom-nav New button, the state badge icons at 14 px.
- Sizes 16 / 20 / 24 (DL §4.3), plus 40 inside the 72 px empty-state circle.
- **Every nav item, document type and action has a distinct glyph** (DL §4.6 map, with these v2 changes):
  - Purchase home uses `layout-dashboard`;
  - Purchase requests use `clipboard-list`;
  - Expense claims use `receipt-indian-rupee` (Lucide's `receipt` shows a dollar sign);
  - Home uses `house`;
  - "Saved" uses `cloud-check`;
  - help uses `circle-help`;
  - the info tip uses `info`;
  - network error uses `wifi-off`;
  - 404/403 uses `file-question`;
  - quick-create uses `user-plus`;
  - recent picks use `history`.
- Icon + label on every primary action, and on secondary actions where a familiar verb icon exists. Icon-only only for: menu, close, back, more, move up/down, remove-line, show password, calendar. Each of those has an `aria-label`.
- Status icons on every state badge and banner (DL §3.1 state map).
- Section icon tiles: a 36 px accent-50 tile with an accent-700 20 px glyph beside each card heading. That is the "icon beside every heading" DL §4.9 calls noise, so it is allowed **only** on card headings in forms and the home, never on field labels.

**Motion** (owner, 01-11; replaces DL §6.1 durations, keeps its rules): `--dur-fast` 150 ms (press, hover, switch, chip), `--dur-base` 200 ms (fades, picker list, errors appearing, toasts out), `--dur-slow` 250 ms (sheets, drawer, toast in, step change). Easing `--ease-out` = `cubic-bezier(0.2, 0, 0, 1)` for entering and moving, `--ease-in` = `cubic-bezier(0.3, 0, 1, 1)` for leaving. Only `transform`, `translate`, `scale`, `rotate` and `opacity` animate (plus colour on press). Under `prefers-reduced-motion: reduce` every duration becomes 0.01 ms and loops stop. All motion is CSS or lives in existing JS files (`app.js`, `toast.js`, `busy.js`, `upload.js`, `dialog.js`). No inline script and no `hx-on`.

| Motion | Spec | How (CSP-safe) |
|---|---|---|
| Page change (full load) | 150 ms cross-fade, header fixed | `@view-transition { navigation: auto }` + `view-transition-name: header` (Chrome 126+, Safari 18.2+; others instant) |
| Wizard step change | old fades out 100 ms; new fades in from `translate: 8px 0` in 200 ms (reversed on Back) | `hx-swap="… transition:true"` on step forms + `::view-transition-*(wizard)`; `data-nav="back"` set by `app.js` on `htmx:beforeTransition` |
| htmx fragment swaps | new content fades in 200 ms | `.htmx-added { opacity: 0 }` → transition on settle |
| Sheets (picker, New, quick-create, nav drawer) | slide up `translate: 0 24px` → 0 + fade, 250 ms; drawer from start edge; exit 200 ms | `@starting-style` on `dialog[open]`; `transition-behavior: allow-discrete` for exit where supported |
| Picker list | fades in 200 ms (dropdown: + `translate: 0 -4px`) | `@starting-style` on the listbox when it becomes visible |
| Toast | slides in from `translate: 0 16px` 250 ms; fades out 200 ms | `toast.js` adds `.leaving`, waits for `transitionend` (DL §6.4) |
| Pressed | buttons, cards, nav: `scale: 0.98` + accent-100 / accent-800 in 150 ms | `:active` |
| Field error appears | fade + `translate: 0 -4px` → 0, 200 ms; no shake | error region swapped, `htmx-added` |
| Info tip opens | content fades in 200 ms | `details[open]` |
| Skeleton | 1.4 s shimmer loop only while loading; static under reduced motion | `@keyframes` on `.skeleton` (daisyUI `skeleton` allowed) |
| Success tick (submit, approve) | circle draws in 400 ms, check draws 250 ms after it | SVG `stroke-dashoffset` keyframes in CSS, on the flash success block; instant under reduced motion |
| Loading bar | indeterminate 3 px bar, appears only after 300 ms | `#loadbar.htmx-request` (§5.14) |

### 5.5 Form patterns

Components: `components.Card` (**changed**: icon, heading, one-line description), `FieldProps` (**changed**: `Required` replaces `Optional`; `Placeholder`; `Tip`), `components.InfoTip` (**new**), `components.MoreDetails` (**new** thin wrapper on `Disclosure`), every input (**changed** look).

1. **Sections as cards.** A form is a stack of cards. Each card has a 36 px icon tile, a heading (18/600) and a one-line description that says what the section is for ("Vendor and delivery: The vendor gets the order; goods come to the site."). A card holds 1–6 fields. Desktop forms stay one column, max 40rem (DS §6); tight pairs (Qty + UoM, Rate + Tax) share a row from 30rem (`.pair`).
2. **Required marking, not "(optional)"** (R15). Required fields get a red asterisk after the label (`aria-hidden`), a visually hidden " (required)" and `aria-required="true"` on the control. Each form with at least one required field starts with the line `Fields marked * are required.` Optional fields carry no marker. This replaces DS §7 `Field`'s "(optional)" rule. The asterisk is a shape as well as a colour, so it meets "never colour alone".
3. **More details** (R15). Fields that most people skip go under a closed `<details>` at the end of their card: summary `+ More details · {what is inside}` (for example `· project, required by`), with a chevron that rotates. It opens automatically when any field inside has a value or an error (server-side `open`). The fields to move are chosen per DocType by a new `Field.More bool` declaration (default false), so docscreen renders them without module code. First users of `More`: PO `Project` (when not restricted) and `Required by`; expense line `Same receipt`, `No receipt`, `Bill in company GSTIN`, `Project or site` (they are disclosures today: they move into one More details); party `Payment terms`, `Active`; setup `State code`, `PAN`.
4. **Inline help with an info "i"** (R14). Short, always-useful help stays as a visible hint under the input (one line at most, for example `Including any GST.`). Longer "why" help sits behind an info button beside the label: a `<details class="infotip">` whose summary is a 44 × 32 px `info` icon with `aria-label` "Help for {label}"; its content is a tinted info box shown under the label row. It works by tap, keyboard and screen reader, with no hover and no JavaScript; `aria-describedby` on the input includes the tip's id. At most one tip per field; format rules and errors are never hidden behind it.
5. **Placeholders as examples.** Every text input that benefits gets `placeholder="e.g. …"` with a real-looking value (`e.g. 27AABCS1429B1ZU`, `e.g. Shree Steel Traders`, `e.g. Diesel for site generator, Panvel`). Placeholders never replace labels (DS §7) and use the muted colour (5.6:1). Date inputs show `dd-mm-yyyy`; money `0.00`.
6. **Helpful error messages.** Inline under the field: `circle-alert` 16 px, danger-800 text, weight 550; the control's border becomes 2 px danger-600; `aria-invalid="true"`, `aria-describedby` → the message. Text says what is wrong and how to fix it, with the field's own words: `PAN has 10 characters: 5 letters, 4 digits, 1 letter. You typed 8.` *(PROPOSED v2 for PAN; kernel and module texts stay as their owners wrote them — CD-147: a v2 text change to an owned message is made by the owning area, not here)*. The error region keeps its reserved line (CD-287).
7. **Booleans as switches** (R12). A single yes/no field is a **switch row**: the label and a one-line explanation on the left, a 48 × 28 px switch at the end, the whole row (≥ 56 px) the target. It uses `<input type="checkbox" role="switch">` (daisyUI `toggle`, allowed). This replaces "Vendor (optional) [ ] Yes" (DL A16). A field whose natural wording is negative (`disabled`) is shown positively (`Active`, on = not disabled) by a declared `Field.Invert` (**new**, display only; the column and import keep the stored meaning).
8. **Short enums as segmented controls; long ones as selects** (R12, R13). Two to four options of ≤ 12 characters each: `components.Segmented` (**existing**, restyled: sunken track, white raised thumb with an accent ring, a check icon on the chosen one). Five to six options with longer words, or those that benefit from big targets: **tiles** (Radios with `Layout: Tiles`, a 2-column grid of the same segmented look; expense Type). Seven or more, or any option list that grows: `components.Select` (GST category becomes a select, R13). Radios with hints stay for choices whose options need a second line (PO vendor address, GRN order).
9. **Two booleans that describe one thing become one segmented choice.** Party `is_vendor` + `is_customer` → `This party is a: Vendor / Customer / Both` (R12). The screen posts one `role` value and the master's Save maps it back to the two columns; import and the API keep the two columns. Q3 covers parties that are neither.

### 5.6 Wizard pattern (R9, R16)

Components: `wizard.Frame` (**changed**), `wizard.Stepper` (**changed**), `components.ActionBar` (**changed** into the sticky footer), `wizard` check page (**changed** look), `layout.Page` focus mode (**new** option `Focus: true`).

**Focus mode.** On phones and tablets (< 64rem), wizard steps, line pages and reason pages hide the app header and the bottom nav. Their own **wizard head** is the sticky top bar:
- a 44 px `×` (or `‹` on a line page), which goes to where the wizard was opened from (the module home, the list, or the Items step). On a document wizard it keeps the saved draft; on a master wizard it confirms `Leave without saving? What you typed in this wizard is lost.` through `Dialog`;
- the document's meta line (`Purchase order`, or the vendor once chosen);
- the h1: `New purchase order` before the first save, then the document label (`Draft 57`);
- the **save cue** at the end: `Not saved yet` (dashed circle, muted), then `Saved 10:42` (`cloud-check`, success-600) after each step save, then `Saving…` while a save runs.

On desktop the app shell stays, and the wizard head is the page head above the stepper.

**One compact step header.** The title appears **once** (the h1 in the wizard head). The stepper is a row of numbered dots joined by lines, with the step labels under the dots from 30rem; below that only the current label shows beside its dot and the others stay readable by screen readers (C2a, CD-364):
- done steps: accent-filled dot with a white check, the label in accent as a link (`Completed: Details` for screen readers);
- current step: an accent ring with a 4 px accent-100 halo; its label is the `<h2 id="step-title">`, described by a visually hidden "Step 1 of 4" (`aria-describedby="step-count"`), and it is the focus target after a step change;
- future steps: a grey ring, plain text.

Labels must be ≤ 12 characters (enforced by a `wizard.Model` validation test), so four or five fit at 320 px. Under the stepper, one muted line says what the step is for (`Step.Intro`, new field). The separate `<progress>` bar and the repeated "Step 1 of 4" text are removed (DL A10, R9). Step labels in v2: PO `Details · Terms · Items · Check`; GRN `Order · Delivery · Quantities · Check` *(PROPOSED v2: "Choose purchase order" → "Order"; the intro says the rest)*; expense claim `Details · Expenses · Check`; party `Party · Addresses · Contacts · Check`; setup `Company · Head office · Check`.

**Sticky footer that never covers fields** (R16, DL A11). The action bar becomes `.footer`:
- the last child of the step, `position: sticky; bottom: 0`, full-bleed on phones, white with a top shadow edge, safe-area padding;
- because it sits in the flow, it never overlaps the end of the form, and `scroll-padding-block-end` (footer height + 8 px, set from a token) keeps a focused field above it;
- it holds an optional summary row (running total), then the buttons: **Back** (secondary, with the `chevron-left` icon, from step 2 on; saves without validating as today) and the primary (`Save and continue`, or `Continue` in master wizards, or the state action on Check), which fills the remaining width;
- from 64rem it is a sticky footer card at the bottom of the form column with the primary at the end, min 14rem;
- `Save and finish later` moves out of the footer: on phones the wizard head's `×` does it (the draft is saved by each step), and on desktop it is a ghost link in the page head (`Finish later`).

E2E check A-12 asserts that for each focusable field in each phone step, after `focus()`, the field's box ends above the footer's top.

**Save-draft cue**: the save cue above. After **Back** or any step save the cue updates from the response (`HX-Trigger: saved` with the time; `app.js` writes it into the cue's live region, `aria-live="polite"`).

**Check and submit**: one summary card per step (icon tile + heading + `Change` ghost button), using `SummaryList` (existing), each section marked `Complete` (success badge) or `Needs attention` (warning badge) when reopened (DS §8.3). Then the totals card (`kv` rows, GST split with its reason line, `AmountInWords`), the approval preview as an info banner, and the footer with the state action (`Submit for approval` with the `send` icon).

**Focus**: the step h2 after a step change, or the ErrorSummary after a 422 (as today). Enter presses the primary (`EnterSubmit`, CD-286).
